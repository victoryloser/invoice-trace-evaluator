# 扩展轨迹导入

所有适配只转换文件结构，不执行 span、工具或用户文本。必须提供用户请求、context、reference_result、两个版本的 run 元数据，以及真实存在的事件证据。缺失业务字段会报错，不由运输格式推断开票事实。

## canonical

标准逐 Case JSONL。校验后保留 Case、run、event_id、seq 和额外字段。

## envelope

每行 `{"task": {...Case除runs外的字段...}, "trajectories": [...原runs数组...]}`。适用于将任务信息与轨迹分别存储的离线工程。使用自己提供的 JSONL；历史 examples/ 文件不发布。

## otel

使用 OTLP JSON 的 `resourceSpans[].scopeSpans[].spans[]` 外层，并显式携带业务证据属性：

```json
{
  "case": {"case_id":"...", "user_request":"...", "context":{}, "reference_result":{}},
  "run_metadata": [{"run_id":"...", "agent_version":"...", "task_id":"...", "trace_id":"...", "final_state":"...", "invoice_created":false}],
  "resourceSpans": [{"scopeSpans": [{"spans": [{
    "attributes": [
      {"key":"invoice.run_id", "value":{"stringValue":"..."}},
      {"key":"invoice.event_json", "value":{"stringValue":"原始完整事件的JSON字符串"}}
    ]
  }]}]}]
}
```

上例缩略展示一个 run；实际每个 Case 必须有两个 run。完整事件字段可通过 `python -m invoice_eval schema` 查看。这是显式的发票业务运输约定，不宣称任意生产 OpenTelemetry 日志都自动具有业务证据。适配器读取离线导出文件，不发布样例轨迹。

适配后另写 `.provenance.json`，记录输入/输出哈希和事件编号保留声明；重新运行严格 loader 检查覆盖和唯一性。

## 时序用户修订扩展

在事件的 `observed_input` 中增加：

```json
{"user_update":{"amount_value":2500,"amount_basis":"tax_exclusive"},"user_confirmation":true}
```

更新先于该事件动作生效。单独提供 `user_confirmation` 只表示当前任务内容的确认。`USER_MESSAGE` 步骤还可包含 `user_request`，对明确金额、取消、暂缓等生成局部修订；复杂语义应通过结构化适配明确其字段和到达时点。`OBSERVATION` 可记录无关观察。未提供这些字段时，按现有事件信息重建状态。

未知受理后的重试要同时有稳定非空 `idempotency_key` 和显式依据：`observed_input.retry_authorized=true` 或工具参数 `retry_basis="idempotent_replay"`。这些字段只在实际已有证据时由导出方填入，适配器不会补造。
